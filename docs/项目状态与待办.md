# 项目状态与待办

更新日期：2026-10-13（日本时间）

## 项目介绍与当前范围

健身卡册是个人使用、无需账号的截图收集与跟练 PWA。使用原生 HTML、CSS、JavaScript，通过 GitHub Actions 发布到 GitHub Pages。照片不上传服务器。

- 仓库：https://github.com/chinheki/fitness-cardbook
- 应用：https://chinheki.github.io/fitness-cardbook/
- 初版代码提交：cb0cb738a2606ce1de1e6f5170e89ecec5c7e113。
- 已实现：多图／文字动作卡、自由标签、可选十字名字、原图查看、多图轮播；随机最多八项／自定义选择、选中置顶、左滑取消、固定底部；次数／时长、组数、休息、暂停、上次参数与粗略节拍；训练历史、完整 JSON 图片备份／恢复、PWA 离线资源。
- 暂缓：训练计划、收藏组合。早期策划中的独立“今日安排”页和旧导航已被第三版交互替代，不应作为待补功能。组合复用等早期构想不应视为已交付。

## 已确认的交互决策

采用“清爽卡册”：以图片为主，不要求命名或分类，不设置单卡“加入今日”。名字与标签叠在左下角，横图靠上完整显示，多图每两秒轮播并遵循减少动态效果设置。

随机后留在卡册勾选，选中项置顶，未选项变灰，可增减数量；底部变成单个大“开始”。随机从当前筛选范围不重复取最多八项，自定义从零项开始。导航为设置／大加号／历史。

点加号选相册，长按拍照；同一动作可追加照片、自建标签，添加成功回卡册。历史按周和日期倒序显示小缩略图。优先缩略图与可见卡片轮播，暂不增加分页或窗口化展示。

## 数据与验证边界

卡片、原图、缩略图、标签、历史保存在 IndexedDB；进行中的训练保存在 localStorage。写入照片与卡片使用同一事务，成功后才提示添加成功。删除卡片保留历史引用图片；完整恢复与清空会替换全部数据，并要求确认。

原会话报告：六项核心逻辑测试、本机 Chromium 导入与刷新保留、选择与训练、备份恢复、离线重开及线上 Pages 检查通过。这些是 2026-10-10 的初版验证记录，本次未重做浏览器或真机检查。

真实 iPhone／Android 安装、相册、拍照、常亮、后台及跨天存储尚未完成可靠验证。当前用户已报告 iPhone 主屏幕版跨天全部丢失，因此不能再把短时刷新成功解释为长期可靠保存。

## P0：iPhone 主屏幕版隔天全部数据丢失（未解决）

### 用户已确认

2026-10-13 当前会话：用户多次反馈本地数据丢失，明确为“iPhone 主屏幕上的卡册隔天全丢”，并补充“我用的 chrome”。尚未确认具体如何从 Chrome 安装、当前启动 URL、iOS／Chrome 版本、独立应用运行模式、是否清理网站数据及设备可用空间。不得将“通过 Chrome 添加”当作用户已明确确认的事实。

### 已检查的代码事实

- 启动读取固定名称 fitness-cardbook、版本 1 的 IndexedDB，不主动清空数据库。
- Service Worker 更新只清理应用资源缓存，未调用 IndexedDB 清空。
- 全量替换入口为用户确认后的恢复备份和清空操作；普通启动未走这些入口。
- navigator.storage.persist() 只在设置按钮中手动调用，启动与添加卡片没有自动申请，也没有持续显示保护状态。
- 有手动完整备份，没有外部自动备份或云同步。

### 尚未证实的解释与纠正

系统存储回收、入口或运行环境变化、写入／读取异常等都需要进一步证据。没有访问用户手机数据库，也未复现隔天丢失。不能断言用户操作错误、Chrome 是原因、Safari 是原因，或自动申请持久存储就能彻底解决。先前“没有证据表明普通启动清空”只代表代码检查结果，不排除尚未发现的应用问题。
